Chapter 1 Event Propagation · Foundations

What is an Event?

Before we get into propagation, let's make sure we understand what an event actually is — because everything in this chapter builds on top of that one idea.

Definition — Event

An event is a signal that something happened — either triggered by the user or by the browser itself. When you click a button, press a key, move your mouse, or submit a form, the browser creates an event object and sends it out into the DOM.

Some common events you'll work with

clickdblclickkeydownkeyup mouseovermouseoutmousemove submitinputchange loadfocusscrollkeypress
  • click — user clicks on an element
  • keydown / keyup — user presses or releases a key
  • mouseover / mouseout — mouse enters or leaves an element
  • submit — user submits a form
  • input — value inside an input field changes
  • load — page or a resource finishes loading

But… what is Event Propagation?

When an event happens on an element in the DOM (for example, you click a button), the browser doesn't just fire the event on that one element and stop. Instead, the event goes on a journey — it travels through the DOM tree, visiting parent and ancestor elements along the way.

This journey is called Event Propagation. The word "propagate" means "to spread or travel". So event propagation literally means: the event spreading / traveling through the DOM.

Concept · the 30-second version

User interacts → browser builds an Event object → the object is dispatched to the target → but it pays a visit to every ancestor on the way down and the way back up. That round trip is propagation.

Attaching a listener

You observe events with addEventListener(). The same element can listen to many event types, and the same event type can have many listeners.

JavaScript basics.js 
const btn = document.querySelector('#child');

// listener function receives the Event object
btn.addEventListener('click', function (event) {
  console.log(event.type);        // 'click'
  console.log(event.target);      // <button id="child">
  console.log(event.currentTarget); // same element here
});

// multiple listeners on the same element are allowed
btn.addEventListener('click', () => console.log('second listener'));
Note · events are objects

The handler always receives an Event instance. Almost everything in this chapter (target, currentTarget, stopPropagation(), composedPath()) is a property or method on that object.

Chapter 1 Event Propagation · The Journey

The Propagation Journey

An event is not a private message to one element — it's a broadcast that walks the family tree. Let's build the intuition with a doorbell, then map it onto the DOM.

Real-life analogy — the doorbell

Analogy · a house with many rooms

Imagine a house with multiple rooms — a main hall, a living room, and a bedroom inside the living room. Someone rings the doorbell. Who hears it? Not just the person in the bedroom — everyone in the house hears it! The sound travels outward through all the rooms.

In the same way, when you click a button deep inside the DOM, the event doesn't stay at the button. It travels through all the parent elements surrounding it.

Understanding the DOM tree

To understand propagation you need to picture HTML as a tree structure — a family tree of nested elements. Every element (except <html>) has a parent, and elements can have children.

Here is the simple HTML structure we'll use throughout this entire chapter:

HTML structure.html 
<!DOCTYPE html>
<html>
  <body>

    <div id="grandparent">
      <div id="parent">
        <button id="child">Click Me!</button>
      </div>
    </div>

  </body>
</html>

Now, when you click the button, the event does NOT just fire on the button alone. It travels up and down this entire tree. Let's understand exactly how.

Careful · window is not an element

window is the global object, not a DOM node — but it does participate in propagation as the outermost stop. That's why window.addEventListener('click', …) hears clicks on any element of the page.

Chapter 1 Event Propagation · The Three Phases

The 3 Phases of Event Propagation

Every event in the browser passes through exactly three phases — in this order, every single time. No exceptions.

Phase 1 · Capturing ↓ Phase 2 · Target Phase 3 · Bubbling ↑
Capturingtop → downwindow → target
Targetarrivesthe clicked element
Bubblingbottom → uptarget → window

Phase 1 — Capturing (top → down)

The event starts its journey from the very top of the DOM — from the window object — and travels downward through each ancestor element, getting closer and closer to the element that was actually clicked (the target).

Think of it as the browser asking each element from top to bottom: "Do you want to react to this event before it reaches the target?" If an element has a capturing listener registered, it will fire during this phase.

Important

By default, event listeners do NOT listen during the capturing phase. You have to explicitly opt in with { capture: true }.

Phase 2 — Target (the event arrives!)

The event has reached the exact element that was interacted with. This is the target element — the element the user clicked, typed in, or hovered over.

Event listeners attached to the target element fire during this phase. Both capturing and bubbling listeners on the target itself will run here.

Phase 3 — Bubbling (bottom → up)

After the event fires at the target, it starts traveling back up through the DOM tree — from the target element, back through its parents, grandparents, all the way up to window.

This is the default phase. When you write a normal addEventListener() without any special options, you are listening in this phase.

Why "bubbling"?

Picture a bubble underwater — it starts at the bottom and rises to the surface. Same here: the event starts at the target and travels up to window.

Code example — seeing all 3 phases

Let's write code that proves all 3 phases exist. We add listeners to all three elements (grandparent, parent, button) — once for capturing, once for bubbling:

JavaScript phases.js 
const grandparent = document.getElementById('grandparent');
const parent      = document.getElementById('parent');
const child       = document.getElementById('child');

// ── CAPTURING listeners (true = capturing phase) ──────────────
grandparent.addEventListener('click', () => {
  console.log('1. Grandparent - CAPTURING');
}, true);

parent.addEventListener('click', () => {
  console.log('2. Parent - CAPTURING');
}, true);

child.addEventListener('click', () => {
  console.log('3. Child - CAPTURING (target reached)');
}, true);

// ── BUBBLING listeners (default - no third argument needed) ───
grandparent.addEventListener('click', () => {
  console.log('6. Grandparent - BUBBLING');
});

parent.addEventListener('click', () => {
  console.log('5. Parent - BUBBLING');
});

child.addEventListener('click', () => {
  console.log('4. Child - BUBBLING (target fires again)');
});

When you click the button, the console outputs in this exact order:

Console output 
1. Grandparent - CAPTURING              ← Phase 1 starts from top
2. Parent - CAPTURING                   ← traveling down...
3. Child - CAPTURING (target reached)   ← Phase 2: reached the target
4. Child - BUBBLING (target fires again)← Phase 3 starts
5. Parent - BUBBLING                    ← traveling up...
6. Grandparent - BUBBLING               ← Phase 3 complete
Key takeaway
  • All capturing listeners fire first (top to bottom).
  • Then the target's own listeners fire.
  • Then all bubbling listeners fire (bottom to top).
  • The numbers in our example (1 → 6) show the exact sequence.

Chapter 2 Event Bubbling

Event Bubbling

Event Bubbling is the default propagation behaviour in every modern browser. You don't have to configure anything to make it work — it is always on.

Definition — Event Bubbling

Event Bubbling is the process where, after an event fires on the target element (the element the user interacted with), that same event automatically travels upward through the DOM tree — firing on each ancestor element one by one — until it reaches the very top (the window object).

This means: if you click a button inside a div, which is inside another div, the click fires on the button first, then the inner div, then the outer div, then body, then html, and finally window.

Why is it called "bubbling"?

Analogy · the swimming pool

Imagine you are at the bottom of a swimming pool and you release an air bubble. That bubble rises upward through the water — passing through every layer — until it finally breaks the surface. An event behaves the same way: it starts at the bottom of the DOM tree (the deepest, most specific element) and rises through every parent element up to window.

Bubbling in detail — step by step

Let's use a concrete HTML example and walk through it so there is no confusion.

HTML boxes.html 
<div id="box-1">
  <div id="box-2">
    <div id="box-3">
      <button id="btn">Click Me!</button>
    </div>
  </div>
</div>

Now we add a click listener to every single element:

JavaScript bubbling.js 
document.getElementById('btn').addEventListener('click', function (e) {
  console.log('Button clicked!  e.target.id =', e.target.id);
});

document.getElementById('box-3').addEventListener('click', function (e) {
  console.log('Box-3 heard it!  e.target.id =', e.target.id);
});

document.getElementById('box-2').addEventListener('click', function (e) {
  console.log('Box-2 heard it!  e.target.id =', e.target.id);
});

document.getElementById('box-1').addEventListener('click', function (e) {
  console.log('Box-1 heard it!  e.target.id =', e.target.id);
});

When you click the button, the output is:

Console output 
Button clicked!  e.target.id = btn   ← fires at the target first
Box-3 heard it!  e.target.id = btn   ← bubbles up to box-3
Box-2 heard it!  e.target.id = btn   ← bubbles up to box-2
Box-1 heard it!  e.target.id = btn   ← bubbles up to box-1
Notice this

e.target.id is always 'btn' — even when the box-3, box-2 and box-1 handlers are running. That's because e.target always refers to the element that was ORIGINALLY clicked. It never changes during bubbling. (Next section explains this in full.)

Chapter 2 Event Bubbling · The key distinction

e.target vs e.currentTarget

This is one of the most commonly tested concepts in interviews. You must understand both properties clearly — they look similar but answer two completely different questions.

Two properties, two questions
PropertyWhat it refers to
e.target The actual element the user clicked / interacted with. never changes as the event bubbles up.
e.currentTarget The element whose event listener is currently running. changes at every level of bubbling.

Code that shows the difference clearly

HTML nested.html 
<div id="outer">
  <div id="inner">
    <button id="btn">Click</button>
  </div>
</div>
JavaScript target-vs-currentTarget.js 
document.getElementById('outer').addEventListener('click', function (e) {
  console.log('--- Outer handler running ---');
  console.log('e.target.id:        ', e.target.id);        // always 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id); // 'outer'
});

document.getElementById('inner').addEventListener('click', function (e) {
  console.log('--- Inner handler running ---');
  console.log('e.target.id:        ', e.target.id);        // always 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id); // 'inner'
});

document.getElementById('btn').addEventListener('click', function (e) {
  console.log('--- Button handler running ---');
  console.log('e.target.id:        ', e.target.id);        // 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id); // 'btn' (same here)
});
Console output 
--- Button handler running ---
e.target.id:          btn
e.currentTarget.id:   btn

--- Inner handler running ---
e.target.id:          btn      ← still btn! It never changes.
e.currentTarget.id:   inner    ← this changes at each level

--- Outer handler running ---
e.target.id:          btn      ← still btn!
e.currentTarget.id:   outer    ← changed again

Interactive — the two values side by side

Simple way to remember this
  • e.target = "WHO started this event?" — the original clicker. Never changes.
  • e.currentTarget = "WHO is handling this event right now?" — changes at every step.
Gotcha · this inside the handler

In a normal (non-arrow) handler, this is the same as e.currentTarget. Arrow functions don't rebind this, so prefer e.currentTarget when you need the listening element.

Chapter 2 Event Bubbling · Control

Stopping Bubbling

Sometimes you want an event to stay on the element it was triggered on and not bubble up to parent elements. That's what stopPropagation() is for.

Once stopPropagation() is called, the event stops travelling. Parent elements will NOT receive the event.

JavaScript stop.js 
button.addEventListener('click', function (e) {
  e.stopPropagation();       // ← event dies here, no bubbling
  console.log('Button handled');
});

Real-world example — card with a delete button

Imagine a list of product cards. Clicking anywhere on the card opens the product detail page. But each card also has a small Delete button. If you click Delete, you want to delete the card — NOT open the product page.

Without stopPropagation, clicking Delete would also trigger the card's click handler (because of bubbling), causing the product page to open. That's wrong behaviour.

HTML card.html 
<div class="card" id="card-1">
  <h3>iPhone 15</h3>
  <p>Price: ₹79,999</p>
  <button class="delete-btn">Delete</button>
</div>
JavaScript card.js 
// Click on the CARD → open product page
document.getElementById('card-1').addEventListener('click', function () {
  console.log('Opening product detail page...');
});

// Click on the DELETE BUTTON → delete the card, do NOT open product page
document.querySelector('.delete-btn').addEventListener('click', function (e) {
  e.stopPropagation();  // ← Stops bubbling! Card's handler will NOT fire.
  console.log('Card deleted!');
  this.closest('.card').remove();
});

// Without stopPropagation - clicking Delete would print BOTH:
//   'Card deleted!'
//   'Opening product detail page...'   ← unwanted!

// With stopPropagation - clicking Delete prints ONLY:
//   'Card deleted!'                    ← correct!

stopPropagation() vs stopImmediatePropagation()

Two methods stop event travel, and they behave slightly differently:

Which one stops what?
MethodWhat it does
e.stopPropagation() Stops the event from travelling to PARENT elements. But other listeners on the SAME element will still fire.
e.stopImmediatePropagation() Stops everything — no parent elements will receive it, AND no other listeners on the SAME element will fire either.
JavaScript immediate.js 
// Suppose the button has TWO click listeners:
btn.addEventListener('click', function (e) {
  e.stopPropagation();          // stops bubbling to parents
  console.log('Listener 1 fired');
  // Listener 2 on the same button will still fire!
});

btn.addEventListener('click', function () {
  console.log('Listener 2 fired'); // This still runs!
});

// If you use stopImmediatePropagation() in Listener 1 instead:
btn.addEventListener('click', function (e) {
  e.stopImmediatePropagation(); // stops everything
  console.log('Listener 1 fired');
  // Listener 2 will NOT fire
});

Interactive — the three scenarios

Warning · don't overuse it

stopPropagation() breaks the contract other code may rely on — analytics, delegated handlers, global click-outside listeners. Reach for it only when an interaction is genuinely isolated.

Chapter 2 Event Bubbling · The big pattern

The Power of Bubbling — Event Delegation

Event Delegation is one of the most important patterns in JavaScript. It is made possible entirely because of event bubbling.

Definition — Event Delegation

Instead of adding a separate event listener to every child element, you add a SINGLE listener on the parent element. When any child is interacted with, the event bubbles up to the parent, and you check e.target to figure out which child was actually clicked.

Click a childtargete.target = button
Event bubblesancestorsli → ul → body
Parent listensone handleron <ul>
Identify childinspect targetclosest('.item')

The problem without delegation

Imagine a shopping cart with 50 items. Each item has a "Remove" button. Without delegation you'd write:

JavaScript bad.js 
// ❌ Bad approach - 50 separate listeners!
const removeButtons = document.querySelectorAll('.remove-btn');

removeButtons.forEach(function (btn) {
  btn.addEventListener('click', function () {
    this.parentElement.remove();
  });
});

// Problems with this approach:
// 1. Creates 50 event listeners in memory - wastes resources
// 2. If you add a new item to the cart dynamically (via JavaScript),
//    the new item's button has NO listener - it won't work!
// 3. More code = harder to maintain

The solution with event delegation

HTML cart.html 
<ul id="cart">
  <li class="item" data-id="101">
    <span>Nike Shoes</span>
    <button class="remove-btn">Remove</button>
  </li>
  <li class="item" data-id="102">
    <span>Adidas T-shirt</span>
    <button class="remove-btn">Remove</button>
  </li>
  <li class="item" data-id="103">
    <span>Puma Cap</span>
    <button class="remove-btn">Remove</button>
  </li>
  <!-- ... imagine 50 items -->
</ul>
JavaScript good.js 
// ✅ Good approach - ONE listener on the parent <ul>
document.getElementById('cart').addEventListener('click', function (e) {

  // Check if the clicked element is a remove button
  if (e.target.classList.contains('remove-btn')) {

    // e.target is the button - .closest() finds the parent <li>
    const item = e.target.closest('.item');
    const itemId = item.dataset.id;

    console.log('Removing item with ID:', itemId);
    item.remove();
  }
});

// This works for ALL current AND future items added dynamically!

Event delegation works because when you click the Remove button inside an <li>, the click event bubbles up from the button → <li> → <ul>. The listener on <ul> catches it, checks e.target, and handles it appropriately.

Chapter 2 Event Bubbling · The exceptions

Which Events Do NOT Bubble?

Most events bubble, but some important ones do not. You need to know these, because if you try to use event delegation with them, it simply won't work.

Non-bubbling events and their bubbling alternatives
Event (does NOT bubble)Bubbles?Use this instead (bubbles)
focus✗ nofocusin bubbles
blur✗ nofocusout bubbles
mouseenter✗ nomouseover bubbles
mouseleave✗ nomouseout bubbles
load✗ nonone — attach directly to the element
scroll✗ nonone — attach directly to the scrolling element
click✓ yes—
input✓ yes—
keydown✓ yes—
submit✓ yes—

Why does this matter?

Concept
  • If you try to do event delegation using 'focus', it won't work — focus doesn't bubble.
  • Use 'focusin' instead: it behaves the same but does bubble, making delegation possible.
  • Example: document.addEventListener('focusin', handler) ← works for all inputs on the page.
JavaScript focusin.js 
// ❌ Won't work for delegation: focus does not bubble
form.addEventListener('focus', handler);       // only fires on form itself

// ✅ Works: focusin bubbles up from every input
form.addEventListener('focusin', function (e) {
  console.log('focused element:', e.target.name);
});

// ✅ Works: focusout bubbles too
form.addEventListener('focusout', function (e) {
  console.log('left element:', e.target.name);
});

Chapter 3 Event Capturing

Event Capturing

Event Capturing is the first phase of event propagation — the phase that happens before bubbling. It travels the opposite way: from the top downward toward the target.

Definition — Event Capturing

Event Capturing (also called the "trickle down" phase) is the process where the browser starts at the very top of the DOM — at the window object — and travels DOWNWARD through each ancestor element, moving closer and closer to the target.

During this downward journey, if any ancestor element has a capturing listener registered for this event type, that listener fires before the event ever reaches the target.

Capturing is NOT the default behaviour. You must explicitly opt in by passing { capture: true } as the third argument to addEventListener().

Real-life analogy — security checkpoint

Analogy · the VIP venue

Before any guest can reach the main stage (the target element), they must pass through multiple security checkpoints at the entrance, in the lobby, and outside the hall. These checkpoints happen before the guest reaches the stage — and they can stop the guest early if needed. Capturing gives ancestor elements a chance to react to (or even block) an event before the target ever sees it.

How to enable capturing

The third argument to addEventListener() controls which phase you are listening in:

JavaScript options.js 
// BUBBLING (default) - listens in Phase 3
element.addEventListener('click', handler);                    // no 3rd arg = bubbling
element.addEventListener('click', handler, false);             // false = bubbling

// CAPTURING - listens in Phase 1
element.addEventListener('click', handler, true);              // true = capturing
element.addEventListener('click', handler, { capture: true }); // same thing

// Modern way - options object (recommended for clarity)
element.addEventListener('click', handler, {
  capture: true,   // listen during capturing phase
  once: true,      // auto-remove listener after it fires once (bonus feature)
  passive: true    // tells browser this handler won't call preventDefault()
});
Reader-friendly options
OptionMeaning
captureRun the handler during the capturing phase (top → down).
onceRemove the listener automatically after its first call.
passivePromise not to call preventDefault() — lets the browser scroll immediately.
signalPass an AbortSignal to remove many listeners at once.

Capturing vs Bubbling — complete side-by-side

This is the most important example in this chapter. Read through it carefully.

HTML levels.html 
<div id="level-1">
  <div id="level-2">
    <div id="level-3">
      <button id="btn">CLICK</button>
    </div>
  </div>
</div>
JavaScript capture-vs-bubble.js 
const l1  = document.getElementById('level-1');
const l2  = document.getElementById('level-2');
const l3  = document.getElementById('level-3');
const btn = document.getElementById('btn');

// ── CAPTURING LISTENERS (true) ─────────────────────────────────
l1.addEventListener('click', () => console.log('[CAP] Level-1'), true);
l2.addEventListener('click', () => console.log('[CAP] Level-2'), true);
l3.addEventListener('click', () => console.log('[CAP] Level-3'), true);
btn.addEventListener('click', () => console.log('[CAP] Button'), true);

// ── BUBBLING LISTENERS (default) ───────────────────────────────
l1.addEventListener('click', () => console.log('[BUB] Level-1'));
l2.addEventListener('click', () => console.log('[BUB] Level-2'));
l3.addEventListener('click', () => console.log('[BUB] Level-3'));
btn.addEventListener('click', () => console.log('[BUB] Button'));

When the button is clicked, here is the exact output:

Console output

[CAP] Level-2
[CAP] Level-3

Read that output again

Stopping an event during capturing

You can call e.stopPropagation() inside a capturing listener. This prevents the event from travelling any further — it will NEVER reach the target element or any other elements below.

JavaScript intercept.js 
// Scenario: stop the event at Level-2 during capturing.
// The button and Level-3 will NEVER receive this event.

l2.addEventListener('click', function (e) {
  e.stopPropagation();   // ← Event stops here. Nothing below fires.
  console.log('Event intercepted at Level-2 during CAPTURING');
}, true);                // true = capturing phase

// When the button is clicked, output is ONLY:
//   [CAP] Level-1                                  ← capturing started
//   Event intercepted at Level-2 during CAPTURING  ← stopped here
// Nothing else fires - not Level-3, not button, not any bubbling handlers
Use this with caution

Stopping propagation during capturing is very aggressive. You are completely preventing the target element from receiving its own event. Only use it when you intentionally want to block child elements from receiving an event — for example, during a modal overlay where background elements should be unresponsive.

Real-world use cases for capturing

Capturing is uncommon in everyday development. Here are the scenarios where it genuinely makes sense:

1 · Blocking interactions during a modal

JavaScript modal.js 
// When a modal is open, block ALL clicks from reaching the page behind it
document.addEventListener('click', function (e) {
  if (modalIsOpen && !modal.contains(e.target)) {
    e.stopPropagation();  // block clicks outside modal
    e.preventDefault();
  }
}, true); // must use capturing to intercept BEFORE target receives it

2 · Global analytics / click tracking

JavaScript analytics.js 
// Track every single click on the page before any handler processes it
window.addEventListener('click', function (e) {
  analytics.track({
    element:   e.target.tagName,
    id:        e.target.id,
    class:     e.target.className,
    timestamp: Date.now()
  });
  // We don't stopPropagation here - we just want to record, not block
}, true); // capturing ensures we run BEFORE any element's own handlers
When to choose which phase
GoalPhase to use
Normal app logic, delegation, most UI codebubbling default
Observe / record clicks before app logic runscapturing
Block events from reaching a region (modal, overlay)capturing + stopPropagation()
Global keyboard shortcuts that can pre-empt widgetscapturing
Delegation of child interactionsbubbling

Chapter 4 Event Traversal

Event Traversal

Event Traversal is the technique of navigating through the DOM tree from inside an event handler — moving from the element that was actually clicked to the element you want to work with.

Definition — Event Traversal

When an event fires, you receive an event object (e). This object gives you e.target — the exact element the user interacted with. But very often, e.target is NOT the element you want to act on.

For example: you click on a small <img> icon inside a <button> inside a <li> inside a <ul>. The e.target is the <img>. But you want to find and work with the parent <li>.

Event Traversal is the process of navigating from e.target to the correct ancestor or descendant — using DOM properties and methods like .closest(), .parentElement, .children and .matches().

Real-life analogy — finding your seat's row

Analogy · the cinema hall

You're in a cinema. You dropped your ticket (the event target — the exact seat). But you need to find the row number (the ancestor element you care about). Instead of reading the entire cinema layout, you look at the seat, then look to the side to find the row label — you traverse from the specific (seat) to the general (row). That's exactly what event traversal does in code.

The most important tool — .closest()

.closest(cssSelector) is the most powerful and most used method for event traversal. Starting from the element it's called on, it walks UP the DOM tree and returns the first ancestor that matches the given CSS selector. If no match is found, it returns null.

A realistic scenario where .closest() is essential

JavaScript tasks.js 
// ONE listener using delegation + traversal
document.getElementById('task-list').addEventListener('click', function (e) {

  // e.target could be any element inside the <li>
  // We need to find WHICH <li> was interacted with
  const taskItem = e.target.closest('.task-item');

  // If nothing matching '.task-item' found up the tree, stop
  if (!taskItem) return;

  const taskId = taskItem.dataset.taskId;

  // Now check WHICH button was clicked
  if (e.target.classList.contains('btn-complete')) {
    taskItem.style.opacity = '0.5';
    console.log('Task', taskId, 'marked as complete');
  }

  if (e.target.classList.contains('btn-delete')) {
    taskItem.remove();
    console.log('Task', taskId, 'deleted');
  }
});

This single event listener handles every button in every task item — current and future ones — using delegation + traversal together. This is the most practical pattern in real frontend development.

Using .matches() to check element type

element.matches(cssSelector) returns true if the element matches the given CSS selector, and false if it does not. It is useful for checking what was clicked inside a delegated handler.

JavaScript matches.js 
document.addEventListener('click', function (e) {

  // Did the user click any button?
  if (e.target.matches('button')) {
    console.log('Some button was clicked');
  }

  // Did the user click a submit button specifically?
  if (e.target.matches('button[type="submit"]')) {
    console.log('Submit button clicked');
  }

  // Did the user click an element INSIDE a .card?
  // (combine with closest for more power)
  if (e.target.closest('.card')) {
    const card = e.target.closest('.card');
    console.log('Clicked inside card:', card.id);
  }

  // Did the user click a link that has a data-action attribute?
  if (e.target.matches('a[data-action]')) {
    e.preventDefault();              // stop the link from navigating
    const action = e.target.dataset.action;
    handleAction(action);
  }

});

Sometimes you need to move to a specific relative element. Here are the traversal properties:

JavaScript relatives.js 
// Practical example - navigating relatives from e.target
document.addEventListener('click', function (e) {

  // Example 1: get the parent
  const parent = e.target.parentElement;
  console.log('Parent:', parent.tagName);        // e.g. 'LI'

  // Example 2: get next sibling
  const next = e.target.nextElementSibling;
  if (next) console.log('Next sibling:', next.className);

  // Example 3: find all <span> elements inside the clicked element
  const spans = e.target.querySelectorAll('span');
  spans.forEach(span => console.log(span.textContent));

});

composedPath() — inspect the full propagation path

e.composedPath() returns an array of ALL elements the event passed through (or will pass through), from the innermost to the outermost. It's very useful for debugging.

JavaScript composed-path.js 
document.addEventListener('click', function (e) {
  console.log('Full propagation path:');
  e.composedPath().forEach(function (el, index) {
    const name = el.nodeName || 'Window';
    const id   = el.id ? '#' + el.id : '';
    console.log(` [${index}] ${name}${id}`);
  });
});

// Clicking a <button id="btn"> inside <div id="wrapper">:
//   [0] BUTTON#btn
//   [1] DIV#wrapper
//   [2] BODY
//   [3] HTML
//   [4] #document
//   [5] Window

Note · closest vs matches

closest() walks up and returns an element (or null). matches() asks a yes/no question about one element. Combine them: use matches() to filter the target, then closest() to find the row.

Interview Q&A

Q1 What is event propagation?›

The journey an event takes through the DOM: it starts at window, travels down to the target (capturing), fires on the target, then travels back up to window (bubbling). All three phases, in that order, every time.

Q2 Difference between e.target and e.currentTarget?›

e.target is the element that actually triggered the event — it never changes. e.currentTarget is the element the currently-executing listener is attached to — it changes at each level of bubbling. Inside an arrow function, use e.currentTarget instead of this.

Q3 Does an event always bubble?›

No. focus, blur, mouseenter, mouseleave, load and scroll don't bubble. Use focusin, focusout, mouseover, mouseout when you need bubbling. You can also check e.bubbles at runtime.

Q4 What's the difference between stopPropagation() and preventDefault()?›

stopPropagation() stops the event from travelling to other elements. preventDefault() cancels the browser's built-in action (following a link, submitting a form). They're independent — one affects travel, the other affects default behaviour.

Q5 Why does event delegation work?›

Because of bubbling: a click on a child bubbles to its ancestors, so one listener on the parent receives events from all current and future children. Then e.target + closest() identify which child was involved. Bonus: fewer listeners and automatic support for dynamically added elements.

Q6 When would you use the capturing phase?›

When you must run before any other handler, or block an event from reaching a region: modal overlays that freeze the page behind, global analytics click tracking, and keyboard shortcuts that should pre-empt widget handlers.

Q7 What does e.composedPath() return?›

An array of all nodes the event will pass through, innermost first — including shadow-DOM boundaries. Handy for "click outside" logic because you can test path.includes(myElement) instead of chaining contains().

Q8 If two listeners are on the same element, which runs first?›

They run in registration order. Capture listeners on that element run before bubble listeners on the same element during the target phase — but stopImmediatePropagation() in the first one prevents the rest from running at all.

Q9 How do you remove a listener?›

removeEventListener(type, handler, options) — the handler reference and the capture flag must match the ones used when adding. Anonymous inline functions can't be removed; use a named reference, once: true, or an AbortController signal.

Q10 What is the target phase exactly?›

The moment the event reaches the target element. Both capturing and bubbling listeners attached directly to the target fire here, in registration order. It's technically not a separate "travel" step — it's the turning point between the down and up journeys.

Cheat sheet

JavaScript cheatsheet.js 
// listen in bubbling (default)
el.addEventListener('click', handler);

// listen in capturing
el.addEventListener('click', handler, { capture: true });

// one-shot listener
el.addEventListener('click', handler, { once: true });

// stop travelling to parents
e.stopPropagation();

// stop everything, including same-element listeners
e.stopImmediatePropagation();

// cancel the browser's default action (not propagation)
e.preventDefault();

// who started it / who is handling it
e.target;         // never changes
e.currentTarget;  // changes per listener

// delegation skeleton
parent.addEventListener('click', (e) => {
  const row = e.target.closest('.row');
  if (!row) return;                       // guard
  if (e.target.matches('.delete')) row.remove();
  if (e.target.matches('.toggle')) row.classList.toggle('done');
});

// debug the path
e.composedPath();
Final mental model

Capture down, target hit, bubble up. Delegation listens on the way up; interception listens on the way down. Everything else is just reading e.target correctly.
