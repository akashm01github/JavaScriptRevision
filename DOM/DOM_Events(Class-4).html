Events — The Foundation

Before propagation, bubbling or capturing make any sense, we must be crystal clear about one thing: what an event actually is. Everything in this class builds on top of it.

◆ Core Concept — What is an Event?

An event is a signal that something happened — an interaction triggered either by the user or by the browser itself. When you click a button, press a key on the keyboard, move your mouse, or submit a form, the browser creates an event object and sends it out through the page.

That event object (often received as e or event in your handler) carries all the details about what happened: which element, which key, which mouse button, the exact coordinates, and much more.

The life of an event — action → object → dispatch (propagation) → handlers

Some common events you'll work with

EventFires when…Family
clickUser clicks on an element (press + release)Mouse
keydown / keyupUser presses or releases a keyKeyboard
mouseover / mouseoutMouse enters or leaves an elementMouse
submitUser submits a formForm
inputValue inside an input field changesForm
loadPage or a resource finishes loadingDocument

Events come in families, and each family's event object carries its own special properties. MouseEvent adds coordinates and buttons, KeyboardEvent adds key/code, and the base Event gives every one of them target, type, and the propagation methods you'll meet in the next chapters.

✦ Note — DOMContentLoaded vs load

DOMContentLoaded fires when the HTML is fully parsed and the DOM tree is ready (images may still be loading). load fires later, when everything — images, stylesheets, iframes — has finished. That's why scripts usually wait for DOMContentLoaded, not load.

Event Propagation

When an event fires, it doesn't stay on one element. It goes on a journey through the whole DOM tree — and that journey has exactly three phases, every single time.

What is Event Propagation?

◆ Definition

When an event happens on an element in the DOM (for example, you click a button), the browser doesn't just fire the event on that one element and stop. Instead, the event goes on a journey — it travels through the DOM tree, visiting parent and ancestor elements along the way.

This journey is called Event Propagation. The word “propagate” means “to spread or travel”. So event propagation literally means: the event spreading / traveling through the DOM.

🏠 Real-Life Analogy — The Doorbell

Imagine a house with multiple rooms — a main hall, a living room, and a bedroom inside the living room.

Someone rings the doorbell. Who hears it? Not just the person in the bedroom — everyone in the house hears it! The sound travels outward through all the rooms.

In the same way, when you click a button deep inside the DOM, the event doesn't stay at the button. It travels through all the parent elements surrounding it.

Understanding the DOM Tree

To understand propagation, you need to picture HTML as a tree structure — a family tree of nested elements. Every element (except <html>) has a parent, and elements can have children. Here is the simple HTML structure we will use throughout this entire chapter:

<!DOCTYPE html>
<html>
  <body>

     <div id="grandparent">
       <div id="parent">
         <button id="child">Click Me!</button>
       </div>
     </div>

  </body>
</html>
HTML as a family tree — every node (except <html>) has a parent

Now, when you click the button, the event does NOT just fire on the button alone. It travels up and down this entire tree. Let's understand exactly how.

The 3 Phases of Event Propagation

Every event in the browser passes through exactly three phases — in this order, every single time:

Phase 1 — Capturing (Top → Down)

The event starts its journey from the very top of the DOM — from the window object — and travels downward through each ancestor, getting closer and closer to the element that was actually clicked (the target).

Think of it as the browser asking each element top-to-bottom: “Do you want to react to this event before it reaches the target?” If an element has a capturing listener, it fires during this phase.

Important: by default, listeners do NOT listen during capturing. You must explicitly opt in.

Phase 2 — Target (The event arrives!)

The event has reached the exact element that was interacted with — the target element. It's the element the user clicked, typed in, or hovered over.

Listeners attached to the target itself fire during this phase. Both capturing and bubbling listeners on the target run here.

Phase 3 — Bubbling (Bottom → Up)

After firing at the target, the event travels back up the tree — target → parents → grandparents → all the way to window.

This is the default phase. A normal addEventListener() with no special options listens here. The name comes from an air bubble rising from the bottom of water to the surface.

Phase 1CAPTURING ↓
window→document→html→body→grandparent→parent→button
Phase 2TARGET ◆
The event fires at: button#child
Phase 3BUBBLING ↑
button→parent→grandparent→body→html→document→window

Code Example — Seeing All 3 Phases

Let's write code that proves all 3 phases exist. We add listeners to all three elements (grandparent, parent, button) — once for capturing, once for bubbling:

const grandparent = document.getElementById('grandparent');
const parent      = document.getElementById('parent');
const child       = document.getElementById('child');

// ── CAPTURING listeners (true = capturing phase) ──────────────
grandparent.addEventListener('click', () => {
  console.log('1. Grandparent - CAPTURING');
}, true);

parent.addEventListener('click', () => {
  console.log('2. Parent - CAPTURING');
}, true);

child.addEventListener('click', () => {
  console.log('3. Child - CAPTURING (target reached)');
}, true);

// ── BUBBLING listeners (default - no third argument needed) ───
grandparent.addEventListener('click', () => {
  console.log('6. Grandparent - BUBBLING');
});

parent.addEventListener('click', () => {
  console.log('5. Parent - BUBBLING');
});

child.addEventListener('click', () => {
  console.log('4. Child - BUBBLING (target fires again)');
});

When you click the button, the console outputs in this exact order:

1. Grandparent - CAPTURING            ← Phase 1 starts from top
2. Parent - CAPTURING                 ← traveling down...
3. Child - CAPTURING (target reached) ← Phase 2: reached the target
4. Child - BUBBLING (target fires again) ← Phase 3 starts
5. Parent - BUBBLING                  ← traveling up...
6. Grandparent - BUBBLING             ← Phase 3 complete
◆ Key Takeaway

All capturing listeners fire first (top to bottom).
Then the target's own listeners fire.
Then all bubbling listeners fire (bottom to top).
The numbers in our example (1 → 6) show the exact sequence.

Event Bubbling

The default propagation behavior in every modern browser — always on, nothing to configure. The event rises from the target to window, like an air bubble rising to the surface.

◆ Definition

Event Bubbling is the process where, after an event fires on the target element (the element the user interacted with), that same event automatically travels upward through the DOM tree — firing on each ancestor element one by one — until it reaches the very top (the window object).

This means: if you click a button that is inside a div, which is inside another div, the click event fires on the button first, then the inner div, then the outer div, then body, then html, and finally window.

🫧 Why is it called “Bubbling”?

Imagine you are at the bottom of a swimming pool and you release an air bubble. That bubble rises upward through the water — passing through every layer — until it finally breaks the surface.

An event behaves the same way: it starts at the bottom of the DOM tree (the target — the deepest, most specific element) and rises through every parent, all the way up to window at the top.

Bubbling: the same event fires on every ancestor, deepest → topmost

e.target vs e.currentTarget — The Most Important Distinction

This is one of the most commonly tested concepts in interviews. You must understand both properties clearly.

PropertyWhat it refers toBehavior while bubbling
e.targetThe actual element the user clicked / interacted with.NEVER changes as the event bubbles up.
e.currentTargetThe element whose event listener is currently running.CHANGES at every level of bubbling.
 
<div id="outer">
  <div id="inner">
    <button id="btn">Click</button>
  </div>
</div>
document.getElementById('outer').addEventListener('click', function(e) {
  console.log('--- Outer handler running ---');
  console.log('e.target.id:        ', e.target.id);         // always 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id); // 'outer'
});

document.getElementById('inner').addEventListener('click', function(e) {
  console.log('--- Inner handler running ---');
  console.log('e.target.id:        ', e.target.id);         // always 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id);  // 'inner'
});

document.getElementById('btn').addEventListener('click', function(e) {
  console.log('--- Button handler running ---');
  console.log('e.target.id:        ', e.target.id);         // 'btn'
  console.log('e.currentTarget.id: ', e.currentTarget.id);  // 'btn' (same here)

e.currentTarget.id:   btn

--- Inner handler running ---

e.target.id:          btn    ← still btn!
e.currentTarget.id:   outer  ← changed again
🧠 Simple way to remember this

e.target = “WHO started this event?” — the original clicker. Never changes.
e.currentTarget = “WHO is handling this event right now?” — changes at every step.

Stopping Bubbling — stopPropagation()

Sometimes you want an event to stay on the element it was triggered on and NOT bubble up to parents. Call event.stopPropagation() inside the handler — once called, the event stops traveling and parent elements will NOT receive it.

stopPropagation() = a dam in the middle of the bubble's path

Real-World Example — Card with a Delete Button

Imagine a list of product cards. Clicking anywhere on the card opens the product detail page — but each card also has a small Delete button. Clicking Delete must delete the card, NOT open the product page. Without stopPropagation, the Delete click would also trigger the card's handler (because of bubbling) — wrong behavior.

<div class="card" id="card-1">
  <h3>iPhone 15</h3>
  <p>Price: ₹79,999</p>
  <button class="delete-btn">Delete</button>
</div>
// Click on the CARD → open product page
document.getElementById('card-1').addEventListener('click', function() {
  console.log('Opening product detail page...');
});

// Click on the DELETE BUTTON → delete the card, do NOT open product page
document.querySelector('.delete-btn').addEventListener('click', function(e) {
  e.stopPropagation(); // ← Stops bubbling! Card's handler will NOT fire.
  console.log('Card deleted!');
  this.closest('.card').remove();
});

// Without stopPropagation - clicking Delete would print BOTH:
// 'Card deleted!'
// 'Opening product detail page...'   ← unwanted!

// With stopPropagation - clicking Delete prints ONLY:
// 'Card deleted!'                    ← correct!

stopPropagation() vs stopImmediatePropagation()

Two methods stop event travel, and they behave slightly differently:

MethodWhat it does
e.stopPropagation()Stops the event from traveling to PARENT elements. But other listeners on the SAME element still fire.
e.stopImmediatePropagation()Stops everything — no parent elements receive it, AND no other listeners on the SAME element fire either.
 
// Suppose the button has TWO click listeners:
btn.addEventListener('click', function(e) {
  e.stopPropagation(); // stops bubbling to parents
  console.log('Listener 1 fired');
  // Listener 2 on the same button will STILL fire!
});

btn.addEventListener('click', function() {
  console.log('Listener 2 fired'); // This still runs!
});

// If you use stopImmediatePropagation() in Listener 1 instead:
btn.addEventListener('click', function(e) {
  e.stopImmediatePropagation(); // stops everything
  console.log('Listener 1 fired');
  // Listener 2 will NOT fire
});

The Power of Bubbling — Event Delegation Pattern

◆ Core Idea

Event Delegation is one of the most important patterns in JavaScript — made possible entirely by bubbling. Instead of adding a separate listener to every child, you add a SINGLE listener on the parent. When any child is interacted with, the event bubbles up to the parent, and you check e.target to figure out which child was actually clicked.

Delegation: bubbling turns 50 listeners into 1

The Problem Without Event Delegation

Imagine a shopping cart with 50 items, each with a “Remove” button. Without delegation:

// ❌ Bad approach - 50 separate listeners!
const removeButtons = document.querySelectorAll('.remove-btn');

removeButtons.forEach(function(btn) {
  btn.addEventListener('click', function() {
    this.parentElement.remove();
  });
});

// Problems with this approach:
// 1. Creates 50 event listeners in memory - wastes resources
// 2. If you add a new item to the cart dynamically (via JavaScript),
//    the new item's button has NO listener - it won't work!
// 3. More code = harder to maintain

The Solution With Event Delegation

<ul id="cart">
  <li class="item" data-id="101">
    <span>Nike Shoes</span>
    <button class="remove-btn">Remove</button>
  </li>
  <li class="item" data-id="102">
    <span>Adidas T-shirt</span>
    <button class="remove-btn">Remove</button>
  </li>
  <li class="item" data-id="103">
    <span>Puma Cap</span>
    <button class="remove-btn">Remove</button>
  </li>
  <!-- ... imagine 50 items -->
</ul>
// ✅ Good approach - ONE listener on the parent <ul>
document.getElementById('cart').addEventListener('click', function(e) {

  // Check if the clicked element is a remove button
  if (e.target.classList.contains('remove-btn')) {

    // e.target is the button - .closest() finds the parent <li>
    const item = e.target.closest('.item');
    const itemId = item.dataset.id;

    console.log('Removing item with ID:', itemId);
    item.remove();
  }
});

// This works for ALL current AND future items added dynamically!

Delegation works because when you click the Remove button inside an <li>, the click bubbles button → li → ul. The listener on <ul> catches it, checks e.target, and handles it appropriately.

Which Events Do NOT Bubble?

Most events bubble, but some important ones do not. You need to know these — if you try to use event delegation with them, it won't work.

If you try to do event delegation using 'focus', it won't work — focus doesn't bubble. Use 'focusin' instead: it behaves the same but DOES bubble, making delegation possible.

Chapter 3 TRICKLE DOWN OPT-IN

Event Capturing

The first phase of propagation — the downward journey that happens before bubbling. Not the default: you must explicitly opt in with { capture: true }.

◆ Definition

Event Capturing (also called the “trickle down” phase) is the process where the browser starts at the very top of the DOM — at the window object — and travels DOWNWARD through each ancestor element, moving closer and closer to the target element.

During this downward journey, if any ancestor has a capturing listener registered for this event type, that listener fires before the event ever reaches the target.

Capturing is NOT the default behavior. You must explicitly opt in by passing { capture: true } (or just true) as the third argument to addEventListener().

🛂 Real-Life Analogy — Security Checkpoint

Imagine a VIP event venue. Before any guest can reach the main stage (the target element), they must pass through multiple security checkpoints — at the entrance, in the lobby, and outside the hall.

These checkpoints happen BEFORE the guest reaches the stage — they can stop the guest early if needed.

Event capturing works the same way: it gives ancestor elements a chance to react to (or even block) an event BEFORE the target element ever sees it.

Capturing = the downward security sweep before the event reaches its target

How to Enable Capturing

The third argument to addEventListener() controls which phase you listen in:

// BUBBLING (default) - listens in Phase 3
element.addEventListener('click', handler);              // no 3rd arg = bubbling
element.addEventListener('click', handler, false);       // false = bubbling

// CAPTURING - listens in Phase 1
element.addEventListener('click', handler, true);        // true = capturing
element.addEventListener('click', handler, { capture: true }); // same thing

// Modern way - options object (recommended for clarity)
element.addEventListener('click', handler, {
  capture: true,   // listen during capturing phase
  once: true,      // auto-remove listener after it fires once (bonus feature)
  passive: true    // tells browser this handler won't call preventDefault()
});

Stopping an Event During Capturing

You can call e.stopPropagation() inside a capturing listener. The event stops traveling — it will NEVER reach the target element or any element below.

// Scenario: Stop the event at Level-2 during capturing
// The button and Level-3 will NEVER receive this event

l2.addEventListener('click', function(e) {
  e.stopPropagation(); // ← Event stops here. Nothing below fires.
  console.log('Event intercepted at Level-2 during CAPTURING');
}, true); // true = capturing phase
[CAP] Level-1   ← capturing started
Event intercepted at Level-2 during CAPTURING   ← stopped here
// Nothing else fires - not Level-3, not button, not any bubbling handlers
⚠ Use this with caution!

Stopping propagation during capturing is very aggressive — you completely prevent the target element from receiving its own event.

Only use it when you intentionally want to block child elements — for example, a modal overlay where background elements should be unresponsive.

Real-World Use Cases for Capturing

Capturing is uncommon in everyday development. Here are the scenarios where it genuinely makes sense:

1. Blocking interactions during a modal

// When a modal is open, block ALL clicks from reaching the page behind it
document.addEventListener('click', function(e) {
  if (modalIsOpen && !modal.contains(e.target)) {
    e.stopPropagation(); // block clicks outside modal
    e.preventDefault();
  }
}, true); // must use capturing to intercept BEFORE target receives it

2. Global analytics / click tracking

// Track every single click on the page before any handler processes it
window.addEventListener('click', function(e) {
  analytics.track({
    element: e.target.tagName,
    id: e.target.id,
    class: e.target.className,
    timestamp: Date.now()
  });
  // We don't stopPropagation here - we just want to record, not block
}, true); // capturing ensures we run BEFORE any element's own handlers

◆ What is a MouseEvent?

Every mouse-driven event (click, mousemove, mousedown…) hands your handler a MouseEvent object. It extends the base Event, so it has everything you already know — target, currentTarget, stopPropagation(), bubbling — plus mouse-specific data: exact coordinates (in 4 different systems!), which button, which modifiers, how fast, and from where the pointer came.

  console.log('offset:', e.offsetX, e.offsetY);   // inside e.target
});
⚠ mousemove fires A LOT — throttle it

mousemove can fire 60–120+ times per second. Never do heavy work (layout reads, DOM writes, network calls) on every event — batch it with requestAnimationFrame:

let ticking = false;
window.addEventListener('mousemove', (e) => {
  if (ticking) return;               // skip events until next frame
  ticking = true;
  requestAnimationFrame(() => {
    updateSomething(e.clientX, e.clientY); // heavy work: once per frame
    ticking = false;
  });
});

Right-click fires contextmenu before the native menu opens. Call e.preventDefault() to block it, then draw your own menu at e.clientX / e.clientY:

⚠ Touch devices don't have a real mouse

On phones/tablets there is no hover, no right-click, and no wheel. Tapping fires compatibility mouse events (mousemove → mousedown → mouseup → click) after the touch events — but hover-based UI simply can't work.

Modern fix: use Pointer Events — pointerdown · pointermove · pointerup · pointerenter · pointerleave. They unify mouse + touch + pen in one API, expose the same coordinates, and add e.pointerType ('mouse' | 'touch' | 'pen') so you can branch when needed.

🎨 CSS :hover vs JS mouseover

For pure visual hover effects, prefer CSS :hover — it's faster and free. Reach for mouseover / mouseenter only when hovering must trigger logic: loading data, starting timers, positioning tooltips.

Event Traversal

Getting from the element that was actually clicked to the element you want to work with — the everyday superpower behind every delegated handler.

◆ Definition

When an event fires, you receive an event object e with e.target — the exact element the user interacted with. But very often, e.target is NOT the element you want to act on.

Example: you click a small <img> icon inside a <button> inside a <li> inside a <ul>. The e.target is the <img> — but you want the parent <li>.

Event Traversal is navigating from e.target to the correct ancestor or descendant — using .closest(), .parentElement, .children, .matches() and friends.

🎟 Real-Life Analogy — Finding Your Seat's Row

You're in a cinema. You dropped your ticket at your exact seat (the event target). But you need the ROW number (the ancestor you care about).

Instead of reading the entire cinema layout, you look at the seat, then glance sideways to find the row label — you traverse from the specific (seat) to the general (row).

That's exactly what event traversal does in code.

From e.target (the button) to whatever you actually need

The Most Important Tool — .closest()

.closest(cssSelector) starts from the element it's called on, walks UP the DOM tree, and returns the first ancestor that matches the selector (it checks the element itself first!). No match → returns null.

    <span class="task-title">Buy groceries</span>
    <div class="task-actions">

      <button class="btn-delete">✖ Delete</button>
    </div>
  </li>

  <li class="task-item" data-task-id="2">
    <span class="task-title">Write assignment</span>

// ONE listener using delegation + traversal
document.getElementById('task-list').addEventListener('click', function(e) {

  // e.target could be any element inside the <li>
  // We need to find WHICH <li> was interacted with
  const taskItem = e.target.closest('.task-item');

  // If nothing matching '.task-item' found up the tree, stop
  if (!taskItem) return;

  const taskId = taskItem.dataset.taskId;

  // Now check WHICH button was clicked
  if (e.target.classList.contains('btn-complete')) {
    taskItem.style.opacity = '0.5';
    console.log('Task', taskId, 'marked as complete');
  }

  if (e.target.classList.contains('btn-delete')) {
    taskItem.remove();
    console.log('Task', taskId, 'deleted');
  }
});

This single listener handles every button in every task item — current and future ones — using delegation + traversal together. This is the most practical pattern in real frontend development.

Using .matches() to Check Element Type

element.matches(cssSelector) returns true if the element matches the selector, false otherwise — useful for checking WHAT was clicked inside a delegated handler.

document.addEventListener('click', function(e) {

  // Did the user click any button?
  if (e.target.matches('button')) {
    console.log('Some button was clicked');
  }

  // Did the user click a submit button specifically?
  if (e.target.matches('button[type="submit"]')) {
    console.log('Submit button clicked');
  }

  // Did the user click an element INSIDE a .card?
  // (combine with closest for more power)
  if (e.target.closest('.card')) {
    const card = e.target.closest('.card');
    console.log('Clicked inside card:', card.id);
  }

  // Did the user click a link that has a data-action attribute?
  if (e.target.matches('a[data-action]')) {
    e.preventDefault(); // stop the link from navigating
    const action = e.target.dataset.action;
    handleAction(action);
  }

});

Interview Q&A

Click a question to reveal the model answer.

Event propagation is the journey an event takes through the DOM tree after firing on an element. The three phases, always in this order:

1. Capturing — window → down to the target (opt-in with { capture: true }).
2. Target — handlers on the clicked element itself fire (both capture- and bubble-registered ones).
3. Bubbling — target → back up to window (the default).

e.target is the element the user originally interacted with — it never changes while the event travels.

e.currentTarget is the element whose listener is currently executing — it changes at every level of propagation. Inside a handler, this === e.currentTarget (for regular functions).

click on <button> inside <li> inside <ul>: li-handler → e.target = BUTTON, e.currentTarget = LI

stopPropagation() — event stops traveling to other elements, but remaining listeners on the same element still run.

stopImmediatePropagation() — stops travel and every remaining listener on the same element.

preventDefault() — completely different job: cancels the browser's default action (navigation, form submit, context menu). Propagation continues normally.

One listener on a parent handles events for all its children by relying on bubbling + checking e.target (usually with .matches() / .closest()).

Benefits: fewer listeners (memory), works automatically for dynamically added children, less code, one central place for logic.

ul.addEventListener('click', e => { const item = e.target.closest('.item'); if (!item) return; if (e.target.matches('.remove-btn')) item.remove(); });

focus, blur, mouseenter, mouseleave, load, scroll (on elements) do not bubble.

For focus delegation use the bubbling equivalents: focusin / focusout. For hover delegation use mouseover / mouseout. For load/scroll there's no bubbling substitute — attach directly to the element.

Pass true or { capture: true } as the third argument of addEventListener.

once: true — listener auto-removes itself after firing one time.
passive: true — promises the handler will never call preventDefault(), letting the browser scroll immediately without waiting (big performance win for touch/wheel).

Rarely — but real cases exist:

1. Modal guard: intercept clicks at document level (capture) and block anything outside the modal before the target ever sees it.
2. Global analytics: record every click before app handlers can stop propagation, so tracking is never missed.

el.closest(selector) walks UP from el (checking itself first) and returns the first ancestor matching the CSS selector, or null.

In delegation, e.target may be a deep child (an icon inside a button inside a row). e.target.closest('.row') reliably finds the row no matter which pixel was clicked.

An array of every node on the propagation path — innermost first: [target, …ancestors, document, window]. It even crosses shadow-DOM boundaries (that's the “composed” part). Perfect for debugging “who could have heard this event?”.

Yes. stopPropagation only stops the event from traveling to other elements. Listeners on the same element still fire in registration order. To silence Listener 2 as well, Listener 1 must call stopImmediatePropagation().

[CAP] topmost ancestor [CAP] … each ancestor downward [CAP] button ← target reached [BUB] button ← target fires bubbling handlers [BUB] … each ancestor upward [BUB] topmost ancestor

All captures top→down first, then the target (capture-registered then bubble-registered), then all bubbles bottom→up.

mouseover fires again (and mouseout fires on the parent) because they treat children as separate boundaries — and they bubble. mouseenter does NOT re-fire; it only cares about the element's true outer boundary and never bubbles.

⚠ Common Mistakes (exam + production)

1. Using e.target when you mean “my element” inside a handler — that's e.currentTarget.
2. Sprinkling stopPropagation() everywhere — it silently breaks delegation and analytics higher up.
3. Thinking preventDefault() stops bubbling (it doesn't) or that stopPropagation() stops the default action (it doesn't).
4. Delegating with focus/mouseenter — they don't bubble; use focusin/mouseover.
5. Heavy work inside mousemove/scroll without rAF throttling.

Self-Check Quiz

Q1 Which propagation phase is the DEFAULT (what plain addEventListener listens to)?
Bubbling. Without a third argument (or with false), listeners run in Phase 3 — bottom → up. Capturing must be opted into.
Q2 A click on <button id="btn"> bubbles to a handler on its parent <div>. Inside the div's handler, e.target is…
Still the button. e.target never changes during propagation — it's the original interacted element. The div is e.currentTarget in that handler.
Q3 Which method also prevents OTHER listeners on the SAME element from firing?
stopImmediatePropagation() stops travel to other elements AND silences every remaining listener on the current element. (return false only works in old inline on* attributes.)
Q4 You must handle focus for ALL inputs (including future ones) with one listener on document. Which event?
focusin — it behaves like focus but BUBBLES, so one document-level listener catches every input, even ones added later. focus itself never reaches document.
Q5 Levels 1→2→3→button each have [CAP] and [BUB] click listeners. You click the button. The FIRST console line is…
[CAP] Level-1. Capturing runs first, top → down: Level-1 is the topmost ancestor with a capture listener. The button's own handlers come only after the downward sweep finishes.

Practice Problems

P1 · Predict the output

A <div id="a"> contains <div id="b"> which contains <button id="c">. Listeners: on a — bubble; on b — capture; on c — bubble. You click the button. What's the console order?

Order: b (capture) → c (bubble) → a (bubble). Capturing sweep hits b first on the way down; at the target, c's bubble listener fires; then bubbling rises through a. b's capture listener already ran, and b has no bubbling listener.
P2 · Delegate a table

A <table> gets new <tr> rows added dynamically. Highlight (class .selected) whichever row the user clicks — using exactly ONE listener. Rows contain <td>s with <strong> and <span> inside.

table.addEventListener('click', (e) => { const row = e.target.closest('tr'); if (!row || !table.contains(row)) return; table.querySelectorAll('.selected').forEach(r => r.classList.remove('selected')); row.classList.add('selected'); });
closest('tr') handles clicks on any nested td/strong/span, and works for rows added later.
P3 · Modal guard with capturing

While a modal is open, clicks anywhere OUTSIDE the modal must never reach the page behind it. Write the guard.

document.addEventListener('click', (e) => { if (modalIsOpen && !modal.contains(e.target)) { e.stopPropagation(); // block during CAPTURING, before target sees it e.preventDefault(); } }, true);
Capturing is required so the block happens on the way DOWN — otherwise the target's own handlers fire first.
P4 · Why is my new button dead?

You attached .like-btn listeners with querySelectorAll(...).forEach(btn => btn.addEventListener(...)) at page load. Buttons rendered later by JavaScript do nothing. Diagnose and fix without re-running the loop.

Diagnosis: querySelectorAll is a one-time snapshot — listeners were attached only to buttons that existed at that moment. Fix: delegate from a stable ancestor:
feed.addEventListener('click', (e) => { if (!e.target.matches('.like-btn')) return; e.target.closest('.post').classList.toggle('liked'); });
Now every current and future .like-btn works through the single feed listener.
P5 · Build a mini “event inspector”

Create a box that, on every click inside it, prints: the full composedPath (names + ids), e.target vs e.currentTarget, and which mouse button was used. Combine everything from this class.

box.addEventListener('click', (e) => { console.log('path:', e.composedPath().map(n => n.nodeName + (n.id ? '#'+n.id : ''))); console.log('target:', e.target.id, '| currentTarget:', e.currentTarget.id); console.log('button:', ['left','middle','right'][e.button]); });
Bonus: add the same listener with { capture: true } and log the phase difference — you'll see the capture line print first.

A click is never just a click. It is an event object that propagates: captured down from window (if anyone opted in), fired at the target, then bubbled up through every ancestor. You can stop that journey, cancel the browser's default reaction, delegate hundreds of children to one parent listener, and traverse from whatever pixel was hit to whatever element you actually meant.
